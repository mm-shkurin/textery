# Story 17 «Экспорт документа в PDF / DOCX» — состояние на 2026-07-30

Сводка по функционалу для чтения человеком. Источник состояния — `progress-backend.md`;
здесь рассказано, что уже работает, что работает наполовину и чего ещё нет.
Слой frontend по этой истории не начинался вовсе: файла `progress-frontend.md` нет,
макеты и UI-сценарии не трогали.

## Что готово и работает

Экспорт как таковой существует и ходит по всей цепочке: HTTP-роут → usecase → рендерер →
бинарный ответ с файлом. Запрос чужого или несуществующего документа отбивается неразличимо —
владелец вшит в SQL-предикат, так что «чужой документ» и «нет такого документа» дают один и тот
же ответ, и угадать существование чужого id по коду ответа нельзя. Формат экспорта проверяется:
неизвестный или отсутствующий формат получает 422, а не молчаливый фолбэк в PDF — это отдельное
доменное значение `ExportFormat`, а не строковое сравнение в контроллере.

PDF рендерится через WeasyPrint, DOCX — через отдельный рендерер по тому же порту, выбор движка
идёт по формату. Кириллица в содержимом проходит целиком. Пустой документ экспортируется как
валидный файл — отдельного кода под это не писали, дефолтный путь уже справлялся, и это
зафиксировано как сознательный пропуск, а не как забытый сценарий. Экспорт ничего не меняет в
документе: это GET, и на него стоит регрессионный сторож, а не устная договорённость.

Имя файла выводится из заголовка документа и корректно кодируется для кириллицы, включая
случай, когда заголовок пустой или состоит из пробелов — тогда берётся имя по умолчанию.
Сам заголовок при этом появился как новое поле в БД и в API сохранения, с оптимистической
блокировкой (CAS по версии), так что параллельные сохранения не теряются молча.

## Намерение по заголовку: то, чем занят сценарий 3.2

В бизнес-требованиях этого не видно, но последние рабочие единицы ушли именно сюда, и это не
побочная ветка — это то, без чего «документ без заголовка» не имеет однозначного смысла.

Раньше «не трогать заголовок», «поставить заголовок» и «стереть заголовок» ехали через
`str | None`, и различить их можно было только по договорённости. Теперь это тип `TitleUpdate` с
тремя состояниями: `preserve()`, `clear()`, `of(значение)`. Оба правила живут **на типе**, а не в
одном вызывающем: `__post_init__` отклоняет противоречивое «есть значение и при этом стереть» и
сворачивает пустую строку в «не трогать» — на **любом** пути создания, включая прямой
конструктор. Это важнее, чем звучит: раньше защиту от пустого заголовка держал один метод
usecase, и любой другой код, собравший намерение сам (роут, импорт, будущий эндпоинт
создания-с-заголовком), мог отдать в БД `SET title = ''` поверх сохранённого заголовка. Сейчас
это недостижимо по построению.

Отказ по противоречию — типизированный `ValidationException`, а не встроенный `ValueError`:
REST-стек регистрирует обработчики только для этого семейства, иначе клиент получил бы немой
500 на том же сохранении, где уже потерялся его текст. Текст отказа при этом закреплён как
**безопасный для клиента**, а не просто «зафиксированный»: доменные тесты проверяют свойством,
что ни сообщение, ни `error_code` не выносят наружу имя доменного класса и синтаксис
конструктора. Последняя единица закрыла дыру в самом стороже — набор запрещённых фрагментов не
мог сработать на `error_code` (коды пишутся в SCREAMING_SNAKE, там не бывает ни скобок, ни
знака равенства, а имя класса не встречается слитно). Добавлено написание `TITLE_UPDATE`,
выводимое из `__name__`, и — отдельно — контроль, что каждый фрагмент вообще различающий:
переименование класса в `Title` сделало бы фрагментом слово `title`, которое есть и в
безопасном сообщении, и в безопасном коде ошибки, и сторож начал бы обвинять корректный текст.
Теперь в этом случае тесты сообщают «дефект списка фрагментов», а не «утечка».

## Что в работе прямо сейчас

Сценарий 3.2 закрыт примерно наполовину. Гейт `adapters-discovery` пройден, и он дал главный
результат этой сессии — **путь «очистить заголовок» сломан дважды и независимо**:

- **В БД.** `_update_values` строит SET-часть одной веткой, `if title.carries_a_value()`. Для
  `clear()` это False — то же самое, что для `preserve()`, — поэтому очистка попадает в ветку
  «не трогать колонку». На единственном слое, где «очистить» — это реальный SQL, стирание не
  делает ничего.
- **В роуте.** DTO объявляет `title: str | None = None`, и роут пробрасывает значение как есть.
  «Ключа нет» и «прислали явный `null`» — это одно и то же значение в этой строке, а
  `model_fields_set`, единственное место, где они различимы, не читается.

Ни одно из двух не закрывается исправлением другого, поэтому это две отдельные пары шагов.
Следствие: `TitleUpdate.clear()` сегодня не имеет ни одного вызова из продакшн-кода, а
`{"title": null}` — молчаливый 200, который ничего не делает.

Найдено там же и подтверждено на живом коде: порт объявляет `title` только-по-имени
(keyword-only), а адаптер и тестовый DSL — позиционно-или-по-имени (расхождение, которое сегодня
не ломает ничего); `INVALID_TITLE_INTENT` отсутствует в карте статусов и потому уходит как 400,
хотя все четыре его собрата `INVALID_*` — 422; `validation_exception_handler` — единственный
обработчик в файле без единой записи в лог, то есть отказ, который может быть вызван **только**
нашей же ошибкой маршрутизации, — это ровно тот отказ, по которому никого не разбудят.

Всего вставлено десять шагов, в порядке, где каждый выполним к моменту запуска: доменный сторож
(сделан) → БД (ветка очистки + сигнатура) → роут (различить «нет ключа» и `null`, убрать
переходное объединение типов из `execute`) → поверхность ошибки (статус, лог, закрепление самой
строки кода ошибки) → документация контракта → сквозной приёмочный тест на очистку.

## Чего ещё нет

Из бэкенд-сценариев не начаты: защита заголовка от инъекции в HTTP-заголовок ответа,
многобайтовое содержимое как отдельный сценарий рендера, «сохранил и сразу экспортировал»
(свежесть данных), обрезка длинного многобайтового заголовка по границе графемы. Не начата вся
группа устойчивости: внешние URL внутри документа не должны вызывать исходящий запрос,
патологический документ должен обрываться по дедлайну рендера, документ сверх лимита не должен
раскручивать неограниченный рендер, тела ошибок не должны раскрывать внутренние детали, а
падение рендера должно давать атрибутируемый сигнал в логи.

Интеграционные сценарии (корректность PDF и DOCX сквозь всю систему, многобайтовое содержимое
через весь конвейер, экспорт отражает последнее сохранённое состояние) — не начаты.
Сценарии безопасности — не начаты, хотя часть из них уже де-факто обеспечена структурно
(неразличимый отказ по чужому документу, отказ неизвестному формату); их всё равно нужно
закрыть явными тестами, потому что «обеспечено структурно» без теста живёт ровно до следующего
рефакторинга. Нагрузочные и инфраструктурные сценарии — не начаты. Фронтенд — не начат.

## Известные долги, зафиксированные ревью

Оба про «зелёные тесты, которые ничего не доказывают», и оба теперь имеют адресата — шаг,
который обязан их закрыть, а не пожелание на будущее.

Ни один тест в репозитории не отправляет явный `null` в заголовке через HTTP: приёмочный клиент
пишет отсутствие как `title=None` и физически не может отправить явный `null`. То есть вся
защита от затирания живёт внутри usecase — внутри того самого шва, который следующие адаптерные
шаги собираются переделывать. Пока не появится сквозной тест «сохранил заголовок → прислал
`null` → заголовок стёрт», зелёная сборка не доказывает, что заголовки пользователей переживут
релиз.

Читаемые DTO (`DocumentResponseDto`, `DocumentSummaryDto`) не содержат поля `title` вовсе, так
что весь трёхсостоянийный контракт для клиента наблюдаем только через экспорт и разбор заголовка
`Content-Disposition`. Вынести `title` в read-модель — решение соседней истории (story-5-extension
владеет UI заголовка), но связность стоит держать в голове при планировании обеих.
