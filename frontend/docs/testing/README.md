# Тест-кейсы интерфейса

UI-сюиты десяти историй — то, что проверяется в браузере: экраны, состояния,
клавиатура, доступность, поведение при ошибке сети. Это **проектные тест-кейсы**,
а не отчёт автотестов: они пишутся до кода (`/test-spec`), из них растёт TDD-цикл,
и по ним же проверяется готовая история.

Автотесты живут отдельно и в другом масштабе: 960 тестов в `src/**/__tests__`
плюс Selenium-сценарии в `acceptance/tests/frontend/` монорепозитория. Кейс здесь
описывает, **что** должно работать; тест — как это проверено.

## Как читать кейс

Каждый кейс — заголовок `### <номер> <что проверяется>` и блок Gherkin:

```gherkin
Given авторизованный пользователь на экране «Мои проекты»
When он вводит в поиск строку, которой нет ни в одном названии
Then список заменяется пустым состоянием с кнопкой сброса поиска
And заголовок раздела остаётся на месте
```

| Ключевое слово | Что это |
|----------------|---------|
| `Given` | **предусловия** — состояние приложения до шага |
| `When` | **шаги** — действие, которое выполняет проверяющий |
| `Then` / `And` | **ожидаемый результат** — то, по чему кейс считается пройденным |

Формулировки не называют CSS-классы и внутренние идентификаторы: кейс переживает
переверстку, а проверяет он то, что видит и делает пользователь.

## Источник правды

Эти файлы — **копии**. Оригиналы лежат в монорепозитории, в
`ProductSpecification/stories/*/tests/`, и правятся там: у каждого файла здесь в
шапке написан его источник.

```bash
node scripts/sync-test-cases.mjs           # обновить копии
node scripts/sync-test-cases.mjs --check   # упасть, если копии устарели
```

Первую команду нужно выполнять **перед каждым релизным пушем** — иначе
опубликованные кейсы отстанут от тех, которые команда действительно ведёт.
Бэкенд публикует свои пять сюит тем же способом
(`backend/scripts/sync_test_cases.py`).
