# Textery — фронтенд

Приложение на React + TypeScript + Vite для Textery: пользователь выбирает тип
документа, описывает тему, и наблюдает, как сгенерированный ИИ документ
появляется по мере создания.

## Структура

- `src/app` — сборка приложения: роутинг и навигация по флоу (`useFlowNavigation`).
- `src/features/landing` — маркетинговая посадочная страница.
- `src/features/auth` — регистрация, подтверждение кода, вход, сессия.
- `src/features/generation` — процесс генерации документа: модалки выбора
  типа/режима, чат-подобное рабочее пространство, ручной редактор (`ManualEditor`
  на Tiptap), хук поллинга (`useGeneration`) и HTTP-клиенты.
- `src/features/history` — «Мои работы»: два списка с keyset-пагинацией.
- `src/features/projects` — «Мои проекты»: объединённая лента документов и генераций
  с поиском, сортировкой и offset-пагинацией. `q`, `sort` и `page` живут в query string,
  а не в состоянии компонента, поэтому возврат на экран и перезагрузка восстанавливают
  ту же выборку. «Повторить» на упавшей генерации — единственная платная операция экрана,
  и ключ идемпотентности к ней живёт в `useRetryGeneration`.
- `src/styles/fonts.css` — Inter, который раздаётся с собственного origin (`public/fonts/`),
  а не с `fonts.googleapis.com`: сторонний CDN на критическом пути рендера — это лишний
  handshake, точка отказа вне репозитория и хост, который в этом рынке регулярно блокируют.
  Два файла вместо восьми: Inter v20 — вариативный шрифт, `unicode-range` делит его на
  кириллицу (18 КБ) и латиницу (48 КБ).
- `src/shared` — то, что принадлежит не одной фиче: транспорт (`api/`),
  словарь типов документов (`documentTypes.ts`), общие компоненты.
- `scripts/` — гейты CI, которые нельзя выразить конфигом: паритет двух пайплайнов,
  пофайловый пол покрытия, проверка ingress. У каждого рядом лежит `*.selftest.mjs` —
  проверка, которая никогда не падает, ничего не проверяет.

### Слои HTTP

```
shared/api/httpClient  — транспорт; про авторизацию не знает ничего
features/auth/api/authorizedRequest — токен, обновление сессии, повтор запроса
shared/api/send        — httpClient + сессия + читаемый текст ошибки
features/*/api/*Api    — конкретные эндпоинты, перевод wire ⇄ приложение
```

`httpClient` намеренно не знает про токены: клиент, добавляющий токен, импортировал бы
сессию, а клиент `/auth/refresh` тогда импортировал бы клиент, который обновляет токен —
цикл. Поэтому авторизация живёт ровно на слой выше. `auth` здесь не «соседняя фича», а
слой сессии: `generation`, `history` и `documents` стоят на нём, обратных импортов нет.

## Установка и запуск

```bash
npm install
npm run dev           # запуск dev-сервера (проксирует /api на бэкенд)
npm run build         # проверка типов + production-сборка
npm run format        # prettier --write
npm run test:watch    # тесты в watch-режиме
npm run preview       # раздача уже собранного dist/
```

Локальный прогон всех гейтов — тот же список и в том же порядке, в котором их выполняет CI.
Раньше здесь была половина списка, и «прогнал всё локально» означало красный пайплайн на
четырёх шагах, которых тут не было:

```bash
npm run ci:parity     # наборы npm-скриптов в двух пайплайнах CI совпадают
npm run check:ingress # nginx не отвечает 503 сам — см. mayHaveLandedServerSide
npm run audit         # production-зависимости против журнала исключений (без порога)
npm run lint          # oxlint
npm run format:check  # prettier --check
npm run typecheck     # tsc -b --noEmit
npm run test:coverage # тесты + общий и пофайловый пороги покрытия
npm run build         # сборка + бюджеты размера бандла (gzip)
```

## CI

Пайплайнов **два**, и это не дублирование — это две формы репозитория:

- `.github/workflows/frontend-ci.yml` **в корне монорепо** — то, что выполняется на GitHub
  (workflow-файлы читаются только из корня). Отсюда `paths:`-фильтр на `frontend/**`,
  `working-directory: frontend` и сборка docker-образа.
- `frontend/.github/workflows/ci.yml` — standalone-копия. В монорепо она не запускается
  никогда, и выглядит мёртвой. Но `frontend/` выкладывается **в корень** отдельного
  фронтенд-репозитория (`gitverse.ru/studentlabs/slide_frontend`), где этот файл становится
  `.github/workflows/ci.yml` и является там единственным CI. Поэтому в нём нет `paths:` и
  `working-directory`, а `cache-dependency-path` указывает на корневой `package-lock.json`.

Оба выполняют `ci:parity` → `audit` → `lint` → `format:check` → `typecheck` → `test:coverage` →
`build`. Синхронизируются руками — удаление «мёртвой» копии выключает CI в gitverse целиком, — но
уже не на честном слове: шаг `ci:parity` (`scripts/check-ci-parity.mjs`) сравнивает наборы
npm-скриптов в обоих файлах и падает при расхождении. Кроме набора скриптов сравнивается и
**рантайм**: одинаковые гейты на Node 20 и Node 22 — это разные гейты, и такое расхождение
сравнение имён не видит. Версия из `setup-node` в обоих файлах должна совпадать и должна
соответствовать мажору из `engines.node` — вторая проверка работает и в отдельном репозитории,
где сравнивать не с чем. Сравнение двух пайплайнов там пропускается.

Шаг `audit` **не имеет порога severity**. Порог — это молчаливый allow-list: он освобождает и все
нынешние, и все будущие адвизори ниже черты, никак их не называя, и поднять его — самый очевидный
способ заставить гейт замолчать. Вместо порога `scripts/check-audit.mjs` падает на **любом**
production-адвизори, кроме тех, что перечислены в `scripts/auditExceptions.mjs` — с причиной, по
которой приложение неуязвимо, и датой, после которой освобождение перестаёт действовать. Гейт
падает и на просроченной записи, и на записи, которую npm больше не сообщает: журнал, где лежат
мёртвые строки, никто не читает.

Сейчас в журнале одна запись — `GHSA-qwww-vcr4-c8h2` (CSRF в RSC-режиме `react-router`, до
2026-11-01). Здесь нет ни RSC, ни loader'ов, ни action'ов: это SPA на `BrowserRouter`. Версии до
7.17.0 включительно несут четырнадцать собственных адвизори, поэтому 7.18.2 — наименее уязвимый
существующий релиз, а не отложенное исправление.

Шаг `build` заканчивается бюджетами размера (`scripts/bundleBudget.mjs`, gzip): `vite build`
печатает размеры чанков и выходит с нулём, что бы он ни напечатал, — то есть до сих пор единственной
защитой было чтение лога. Бюджеты — это **потолок чуть выше сегодняшних цифр**: их задача — уронить
сборку, когда что-то стало заметно хуже. Чанк без бюджета тоже красный: новый вендорный файл на
400 КБ — ровно та дыра, ради которой гейт добавлен. Поднимать потолок — отдельное решение,
отдельный коммит и причина в сообщении.

Шаг тестов запускается именно с покрытием: пороги живут в `vite.config.ts` и срабатывают только
под `--coverage`. Кроме общих порогов `npm run test:coverage` выполняет
`scripts/check-per-file-coverage.mjs` — пофайловый пол (60% строк, 45% ветвей). Общий процент
не умеет ловить одно: модуль, который не тестирует никто. Тысяча покрытых строк поглощает один
непокрытый файл, не сдвинув процент настолько, чтобы сборка упала. Пороги — это **пол**, зафиксированный чуть ниже текущих цифр; их задача — уронить
сборку, когда покрытие *падает*. Именно так `historyApi.ts` держался на 0% (все вызывающие его
тесты мокали модуль целиком), а сюита оставалась зелёной. Поднимать по мере роста; не опускать,
чтобы починить красный прогон.

## Переменные окружения

Полный список с пояснениями — в `.env.example`; здесь то же самое коротко.

- `VITE_API_BASE_URL` — базовый URL для API генерации. По умолчанию `''`,
  что направляет запросы через прокси `/api` dev-сервера Vite (см. `vite.config.ts`).
- `VITE_API_PROXY_TARGET` — куда dev-сервер пересылает `/api`. Значение по умолчанию
  (`http://127.0.0.1:8100`) верно не для всех: параллельные чекауты публикуют бэкенд на
  разных портах хоста, поэтому берите его из своего `infra/.env` (`grep BACKEND_PORT ../infra/.env`),
  а не отсюда. Никогда `8000` — этот порт на хосте занят другим сервисом, и запросы
  молча уйдут в чужое приложение вместо того, чтобы упасть. Переменная была описана только
  в `.env.example`, из-за чего читатель README её просто не видел.
- `FRONTEND_PORT` — порт, на котором слушает dev-сервер (по умолчанию `5173`).

## Тестирование

Тесты используют Vitest + Testing Library (`src/test/setup.ts`). Перед
коммитом запускайте `npm run test`; `npm run build` также проверяет типы
через `tsc -b`.
