# Как здесь работать

Короткий документ: он описывает только то, что нельзя вывести из кода — порядок работы,
границы и правила, которые в репозитории уже действуют, но нигде не были записаны.

## Прежде чем коммитить

Локально выполняется **тот же** список гейтов и в том же порядке, что и в CI:

```bash
npm run ci:parity && npm run check:ingress && npm run audit && npm run lint \
  && npm run format:check && npm run typecheck && npm run test:coverage && npm run build
```

Красный гейт чинится по причине, а не по симптому. Ни один из порогов —
покрытия, размера бандла, `--max-warnings=0`, журнала адвизори — **не понижается**,
чтобы сборка стала зелёной. Все они зафиксированы чуть выше (или ниже) сегодняшних
цифр именно для того, чтобы падать на ухудшении; порог, который двигают под красный
прогон, не измеряет ничего. Понижение — отдельное решение, отдельный коммит и причина
в сообщении.

## Ветки и коммиты

Pull request'ов в проекте нет: коммиты попадают на рабочую ветку напрямую
(`.claude/rules/workflow.md`). Из этого следует единственное, но важное:
**сообщение коммита — единственная поверхность ревью**. В нём пишется _почему_,
а не _что_ — «что» видно в диффе.

- Conventional Commits: `feat(scope):`, `fix(scope):`, `refactor(scope):`,
  `test(scope):`, `docs(scope):`, `style(scope):`, `chore(scope):`, `build(scope):`.
- Один коммит — одно логическое изменение. Рефакторинг не едет вместе с изменением
  поведения: их нельзя откатить по отдельности, а именно это от них потом и требуется.
- Изменение поведения приезжает вместе со своим тестом.

## Границы

- **200 строк на файл** — жёсткий предел, для любого файла: production-код, тесты,
  стили, конфиги, скрипты. Пределы проверяются глазами (`wc -l`), поэтому файл,
  подошедший к границе, делится **по смыслу**, а не по номеру строки.
- Тесты не удаляются и не переводятся в `skip`, чтобы что-то стало зелёным.
- Заглушки вместо реальной логики — не решение задачи.

## Гейты в `scripts/`

Всё, что нельзя выразить конфигом, живёт в `scripts/` как обычный Node-скрипт, и
рядом с ним лежит `*.selftest.mjs`. Правило одно: **у гейта, который может пройти
молча, должен быть self-тест**. Проверка, которая никогда не падает, ничего не
проверяет, а в CI выглядит ровно так же, как работающая. Новый гейт добавляется
вместе со своим self-тестом и записывается в `scripts/ciRequiredGates.mjs` — иначе
его можно удалить из обоих пайплайнов, и `ci:parity` этого не заметит.

## Два пайплайна

`frontend/` публикуется и как каталог монорепозитория, и как **корень** отдельного
репозитория. Поэтому CI-файлов два (`frontend/.github/workflows/ci.yml` и корневой
`.github/workflows/frontend-ci.yml`), и «мёртвая» копия не мертва — её удаление
выключает CI в отдельном репозитории целиком. Набор гейтов и версия Node в них
сравниваются шагом `ci:parity`; всё остальное (триггеры, `paths:`, `working-directory`)
различается законно. Подробности — в README, раздел «CI».
