# Analytics Event Tracking — Infrastructure Tests

Four failure surfaces this story introduces or changes: the database the events go to, the
geolocation dependency on the registration path, the configuration that dependency and the new
bounds need in order to exist at all, and the periodic sweep whose cost this story raises.

Shared test data for every case below, unless the case names its own:

## 1. The Event Store

### TC-14-INFRA-1.1 — A database that cannot be reached does not take the product down with it

| Field | Value |
|---|---|
| Description | Analytics is a side effect, never a gate: an unreachable event store must refuse only the ingest route and leave registration, sign-in and saving untouched, while still saying loudly that recording was lost. |
| Preconditions | The application is running; the emission adapter's session factory is fault-injected so every event write raises; account A exists and holds one document. |
| Test data | `POST /api/v1/analytics/events` with `{"event_name":"SITE_VISITED","visitor_id":"<uuid>","occurrence_key":"<uuid>","degraded":false,"payload":{}}`; account A's credentials and Bearer token. |
| Steps | 1. Make the database unreachable from the event recorder.<br>2. `POST /api/v1/analytics/events` and read the response body in full.<br>3. Register a new account, sign in as account A, and save account A's document.<br>4. Read the application log for the three product operations. |
| Expected result | Step 2 is refused with a `5xx` carrying the canonical error envelope and no host, port, DSN, password, driver name, SQL text or stack frame. Step 3: register answers `201`, sign-in answers `200` with a token, save answers `200` — status codes and bodies identical to a healthy run. Step 4: for each of `REGISTRATION_COMPLETED`, `LOGIN_SUCCESS` and `DOCUMENT_SAVED` exactly one structured log record is emitted, carrying `event_name` and `visitor_id` as fields — one record per failure, never zero and never a retry storm. |
| Status | Not run |

### TC-14-INFRA-1.2 — Recording resumes by itself once the database returns

| Field | Value |
|---|---|
| Description | A pool that does not recycle dead connections keeps failing after the database is healthy, and recording only resumes when someone restarts the app — at-most-once delivery is a decision, a permanently broken recorder is not. |
| Preconditions | The database container is stopped and at least one event has already been lost (TC-14-INFRA-1.1). |
| Test data | `docker compose -f infra/docker-compose.yml start postgres`; a fresh `visitor_id`; the events lost during the outage recorded by count beforehand. |
| Steps | 1. Record how many events were attempted and lost while the database was down.<br>2. Start the `postgres` container again.<br>3. `POST /api/v1/analytics/events` with `SITE_VISITED` for the fresh visitor, retrying for up to 30 s.<br>4. Confirm the application's process id is unchanged.<br>5. `SELECT count(*) FROM analytics_events` and compare with the pre-outage count. |
| Expected result | Within 30 s the ingest answers `200 {"status":"recorded"}` and one row exists in `analytics_events` for the fresh visitor; the application process id is the one that served the failed requests — no restart, no operator action; the row count equals pre-outage plus the one new event only — none of the events lost during the outage reappears. |
| Status | Not run |

The last line is the point, not an omission: delivery is at-most-once by product decision.
A test asserting recovery of lost events would encode a guarantee the design refuses to make.

### TC-14-INFRA-1.3 — Connections are returned even when recording fails

| Field | Value |
|---|---|
| Description | The failure path is where a session is most often left un-returned; a recorder that leaks a connection per failed write exhausts the pool and takes the product down through the side effect it was built not to gate. |
| Preconditions | The emission adapter is fault-injected to raise on every write; the application is otherwise healthy; the configured `AsyncEngine` is reachable from the test. |

| Expected result | Every one of the 200 operations answers its normal success status; the final `checkedout()` equals the resting value recorded in step 1 — it does not grow with the number of failed writes and never reaches the pool ceiling (5 + 10); no `TimeoutError` on checkout is raised during the run. |
| Status | Not run |

### TC-14-INFRA-1.4 — A start that never gets its completion is detectable

| Field | Value |
|---|---|
| Description | Emission runs after the caller's commit, so a worker aborted in that window leaves `GENERATION_STARTED` with no `GENERATION_COMPLETED`; without a signal the only evidence is an absence in a table nobody reads until Story 15 — and an absence is exactly what a visitor who never generated anything also looks like. |
| Preconditions | A generation whose `GENERATION_STARTED` is stored in `analytics_events`; a second generation that runs to normal completion; the staleness threshold is `GENERATION_STALE_AFTER_MINUTES=10`. |
| Test data | Generation G1: worker aborted after the result row was persisted and before any completion was recorded. Generation G2: completed normally. |
| Steps | 1. Start generation G1 and confirm `GENERATION_STARTED` is stored for it.<br>2. Abort G1's worker after the result is persisted and before emission.<br>3. Run generation G2 to normal completion.<br>4. Advance past the 10-minute staleness threshold.<br>5. Read the structured log / signal stream. |
| Expected result | A structured record exists naming G1's generation id and its `visitor_id` as started-with-no-completion, and it is distinguishable from the swallowed-emission-failure record of TC-14-INFRA-1.1 by its own field set; no such record exists for G2; `analytics_events` holds `GENERATION_STARTED` for G1 with no matching `GENERATION_COMPLETED`, and both rows for G2. |
| Status | Not run |

Emission runs after the caller's commit, so this window is real. Without a signal the only
evidence is an absence in a table nobody reads until Story 15 — and an absence is exactly what
a visitor who never generated anything also looks like.

## 4. The Recovery Sweep

### TC-14-INFRA-4.1 — Two overlapping sweep activations claim each generation once

| Field | Value |
|---|---|
| Description | The existing scenarios cover several instances starting on the same tick; this is the other shape — one activation still running when the next begins, which the un-limited stale query and the un-jittered tick make reachable under a backlog. |
| Preconditions | A backlog of stalled generations large enough that one `RequeueStaleGenerations` activation outlasts its interval; `GENERATION_STALE_AFTER_MINUTES=10`; the sweep runs from the lifespan on its normal tick. |
| Test data | 500 stalled generations, all older than 10 minutes; the sweep's tick interval shorter than one activation's duration; the `analytics_events` counts for `GENERATION_STARTED` and `GENERATION_COMPLETED` recorded before the run. |
| Steps | 1. Seed the 500 stalled generations and record the `GENERATION_STARTED` / `GENERATION_COMPLETED` row counts.<br>2. Begin sweep activation A.<br>3. Begin sweep activation B while A is still running.<br>4. For each generation, count how many activations' conditional updates reported one row affected.<br>5. Re-read the two event counts. |
| Expected result | Every one of the 500 generations is claimed by exactly one activation — the loser's conditional update reports zero rows affected and raises `ConflictException`, which is treated as the normal per-row outcome, never a plain list-then-requeue; no generation is requeued twice; the `GENERATION_STARTED` and `GENERATION_COMPLETED` counts are unchanged by the overlap, since the requeue path emits nothing by design. |
| Status | Not run |

The existing scenarios cover several instances starting on the *same* tick. This is the other
shape: one activation still running when the next begins, which the un-limited stale query and
the un-jittered tick make reachable under a backlog. The event-count assertion elsewhere cannot
catch a double requeue, because the requeue path emits nothing by design — the claim has to be
asserted directly.

**Scope note, 2026-08-19.** This is expected to assert **existing** behaviour, not to require
new: `RequeueStaleGenerations` already claims each row through a conditional update and treats
the loser's `ConflictException` as the normal outcome, per row rather than per sweep. That
mechanism does not care whether the competing claim comes from another replica or from the
previous activation in the same process. Write the scenario, run it against today's code, and
expect green. If it goes red, the sweep has a real defect this story surfaced — report it, do
not fix it inside an analytics work unit.
