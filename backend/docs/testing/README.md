# Тест-кейсы бэкенда

899 тест-кейсов по одиннадцати историям, по пять сюит на историю: 722 в общем
шаблоне (561 базовый и 161 расширенный) и 177 у `14-analytics-event-tracking`,
которые пока в старом формате — см. таблицу ниже. Это **проектные тест-кейсы**, а не отчёт автотестов: они
пишутся до кода (`/test-spec`), из них растёт TDD-цикл, и по ним же проверяется
готовая история.

## Как читать кейс

Каждый кейс — заголовок `### TC-<история>-<сюита>-<номер> — что проверяется` и
таблица из шести полей:

| Поле | Что в нём |
|------|-----------|
| Description | зачем кейс существует — какую поломку он ловит |
| Preconditions | состояние системы до первого шага, с названным аккаунтом и фикстурой |
| Test data | конкретные значения, которые проверяющий вводит: id, тела запросов, пороги |
| Steps | пронумерованные действия, по одному действию на шаг |
| Expected result | точный наблюдаемый результат: код ответа, тело, заголовок, строка лога |
| Status | `Not run` / `Passed` / `Failed` — по нему прогон оставляет след |

Кейс называет коды и тела ответов буквально: их источник —
`api-specs/*.yaml` и обработчики в `adapters/rest/src/error_handling/`. Общая
таблица тестовых данных в начале каждого файла задаёт аккаунты и идентификаторы,
которые кейсы этого файла переиспользуют, чтобы каждый не заводил свои.

## Сюиты

| Файл | Что покрывает |
|------|---------------|
| `01_API_Tests.md` | контракт эндпоинтов: коды, тела, границы валидации, идемпотентность |
| `03_Load_Tests.md` | поведение под нагрузкой: пороги времени ответа, деградация, лимиты |
| `04_Infrastructure_Tests.md` | миграции, рестарт, здоровье экземпляра, конфигурация окружения |
| `05_Security_Tests.md` | аутентификация, чужие ресурсы, раскрытие данных, инъекции |
| `06_Integration_Tests.md` | сквозные сценарии через несколько эндпоинтов и внешние сервисы |

Рядом с базовыми лежит `extended/` — те же пять сюит с дополнительными кейсами
(редкие ветки, гонки, восстановление после сбоя). Базовый набор — то, что
обязано быть зелёным всегда; расширенный — то, что закрывается по мере роста
истории.

`02_UI_Tests.md` здесь нет намеренно: это репозиторий бэкенда, UI-кейсы лежат в
репозитории фронтенда.

`14-analytics-event-tracking` — единственная история, чьи кейсы ещё в старом
Gherkin-формате: заголовок `### 1.1` и блок `Given/When/Then` вместо

проверку без вопросов к автору — нет. Перевод в общий шаблон — отдельная работа;
до неё эта история считается покрытой по замыслу, но не по форме.

## Откуда эти файлы

Копии. Источник правды — `ProductSpecification/stories/*/tests/` в монорепозитории,
который в этот репозиторий не уезжает: там их пишет `/test-spec` и оттуда их
читает рабочий процесс истории. Каждый файл здесь несёт баннер с путём к
оригиналу — правка должна идти туда, иначе следующая синхронизация её затрёт.

Синхронизация:

```bash
python scripts/sync_test_cases.py          # переписать копии
python scripts/sync_test_cases.py --check  # упасть, если копии устарели
```

Запускается из монорепозитория перед публикацией релиза. В опубликованном
репозитории каталога-источника нет, и скрипт честно об этом сообщает вместо того,
чтобы валить пайплайн, который всё равно ничего не может исправить.
